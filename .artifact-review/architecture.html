03

Durability at each boundary

Submission commits a queued record before returning. Workers process independently; a new process can reclaim expired work and reuse completed chunks.

  1. Validate and enqueue

    Pin the provider model, hash the normalized request, atomically insert. An owner-scoped idempotency key reuses the same request; changed input conflicts.

  2. Claim a lease

    PostgreSQL row locks with SKIP LOCKED select one queued or expired job. A fresh token fences out previous workers.

  3. Materialize and fingerprint

    Resolve the source into an attempt workspace. Hash its bytes. Recovery rejects changed media instead of mixing old and new chunks.

  4. Plan and checkpoint chunks

    Inspect duration, save the non-overlapping chunk plan, run bounded parallel tasks, validate provider output, save each completed chunk.

  5. Aggregate and finalize

    Order by chunk index; offset timestamps to the source timeline. Translate if requested. Persist the final result under the same lease.

  6. Clean the attempt workspace

    Cleanup failure does not erase a persisted result. Persistent uploads remain available for later operations.

Lease behavior

Default lease: 60 seconds. Heartbeat: 20 seconds. Every plan, chunk, heartbeat, completion and failure write checks running status, exact token, and unexpired lease.

If heartbeat fails, adapters receive an abort signal. A stale worker cannot checkpoint or finalize. Shutdown stops claims and leaves interrupted work recoverable after lease expiry.

Retry behavior

Provider failure records a failed job. retry explicitly requeues failed jobs and preserves successful chunk outputs. The next attempt rematerializes the original source and verifies its fingerprint.

Model calls are at least once across process failure. A provider response can arrive before its checkpoint is committed; retry may repeat that paid call.

Default work bounds

Two server workers × two chunks per job. SDK chunk limit: 10,000. Adapters add network/process deadlines and media-size limits. These values are configurable where the owning interface exposes them.

Models and persistence

Public job views expose progress and results. Internal records retain ownership, request identity, chunk checkpoints and leases. Schema validation strips those internals from responses.

PostgreSQL · media_v1

jobs stores indexed columns for ID, owner, idempotency key, status, lease token/expiry and creation time, plus the complete record in JSONB.

auth_entries stores key, JSONB value and expiry. migrations records applied migration versions.

A unique owner/key constraint enforces deduplication. Dispatch and owner/date indexes support claiming and recent-job lists. Transactions keep indexed columns and JSONB synchronized.

Persistent volume

uploads/{owner}/{uuid} contains media bytes and filename metadata. Upload IDs are opaque, owner-scoped and derived from content plus filename; atomic deduplication preserves local-file idempotency.

jobs/{owner}/{job}/{attempt} isolates working files. Normal completion and failure clean the attempt directory.

Neon stores job/auth data; it does not store the local upload bytes. Back up the volume separately. Multiple hosts need shared media storage or a replacement adapter.

Scale boundary. Chunk outputs live inside the job’s JSONB record, so checkpoints serialize on that row. This is suitable for a private service; a high-volume deployment can replace the repository with normalized chunk storage without changing the SDK lifecycle.

MCP transport

The official MCP server SDK serves revision 2026-07-28, discovery and JSON responses over Streamable HTTP. Tools are filtered by the caller’s scopes and use the same dispatcher as REST.

07

Private service.
Owner-approved agent access.

A single configured owner token authenticates direct API/CLI use. OAuth gives agent clients scoped, expiring tokens after approval by that owner.

Agent connection flow

  1. Discover resource and issuer

    The 401 challenge points to protected-resource metadata. The issuer advertises authorization, token, registration and revocation endpoints.

  2. Resolve client identity

    Modern clients provide an HTTPS Client ID Metadata Document. Legacy clients register through DCR. Metadata includes the exact client ID, name and redirect URIs.

  3. Approve the requested scope

    A browser consent form shows client, redirect and requested permissions. A same-origin POST, owner token and one-use browser-bound consent record are required.

  4. Exchange with PKCE

    A 60-second, single-use authorization code is bound to client, redirect, resource and S256 verifier. Successful exchange issues a one-hour opaque token.

  5. Enforce each request

    Validate expiry, exact resource and scopes. A token for /mcp cannot be reused at the REST API origin.

CIMD + DCR

Client metadata retrieval accepts HTTPS JSON, pins a public address after DNS resolution, rejects private/mixed DNS answers and redirects, and caps response size/time. No credentials accompany the fetch.

DCR remains for compatibility. Public clients use no client secret; native clients may register HTTP loopback redirects. Other redirects require HTTPS and exact matching.

Deliberate scope

Only media:read and media:write. No user accounts, tenants, refresh tokens or social login. DCR registrations expire after 30 days; clients can re-register.

Token and code values are not stored in plaintext. PostgreSQL atomically consumes grants across processes. Browser consent is protected against replay and cross-origin submission.

Deployment boundary

Use HTTPS at the public origin; loopback HTTP is for development. The ingress must preserve the configured authority and provide shared rate limiting for an internet-facing installation.

CIMD metadata hosts currently require a public IPv4 address. Per-process limits are not a distributed abuse-control service.

08

Concrete media integrations

Production adapters implement the SDK ports. Network and process work stays here; the orchestration layer remains independent.

Source adapters

  • HTTP: public-address validation, pinned DNS, bounded streamed download.
  • YouTube / Instagram / X: single-item URLs through restricted yt-dlp registry entries.
  • Google Drive: one file, using configured Google credentials.
  • Telegram: one post through the configured proxy.
  • Upload: owner-scoped opaque ID backed by the volume.
  • Local file: SDK embedding only; rejected at remote submission.

Provider adapters

  • OpenAI: audio transcription and text translation.
  • Gemini: native video/audio transcription, understanding and translation; uploaded files are cleaned up.
  • Google Speech: transcription using Google credentials and recognizer configuration.
  • Codex: experimental native subscription ASR; prepared frame/transcript understanding.
  • Claude Code: prepared frame/transcript understanding; Codex supplies ASR when audio exists.

Submission stores the resolved model. Provider output is schema-checked before checkpointing. Subscription failure never silently selects a paid API.

08b

Prepare the evidence.
Then start the agent.

Codex and Claude understanding receive timestamped frames and the available transcript in their initial context. Neither agent is asked to discover files, download media or invent an audio transcription.

Provenance stays explicit

provider: codex with transcription uses the route label codex-realtime-v3. The actual ASR backend model is unknown: provenance.transcription.model is null.

For understanding, the top-level provider/model identifies Codex or Claude. Transcript provenance still names Codex, and frameIntervalMs records sampling. Claude Code is never advertised as a native transcription provider.

Translation stays on the selected subscription agent. No API-key fallback, proxy substitution or hidden paid call is allowed.

Dedicated native authentication

Container pins: Codex 0.163.0, Claude Code 2.1.309. Native login persists in separate writable volumes at /auth/codex and /auth/claude.

MEDIA_CODEX_HOME and MEDIA_CLAUDE_HOME select those dedicated stores. Per-home locks serialize CLI access; stale locks require operator inspection. The host’s normal agent homes are not reused.

Subprocesses receive an allowlisted environment and isolated working directory. Prepared input/output, deadlines, abort and process cleanup are bounded.

09

Alignment is a build concern

The operation catalog is executable input to each surface. CI then checks the boundaries and packaged result, so alignment does not depend on remembering to edit parallel command lists.

Contract enforcement

  • REST routes, CLI commands and MCP tool registration iterate the same operation IDs.
  • Every operation defines input/output schema, method, path, description and scope.
  • The client validates requests and responses; the dispatcher validates them again.
  • Before each POST, the client compares its contract hash with server info. The server also rejects a mismatched supplied hash.
  • E2E asserts exact MCP/catalog parity and stale-contract rejection.

Repository and release gates

  • pnpm workspace packages use one release version.
  • TypeScript, oxlint and oxfmt are required checks.
  • Boundary checks prohibit CLI/client imports of execution infrastructure.
  • Release preparation packages the CLI with its skill and workspace dependencies, alongside the API release.
  • Database-backed tests cover races and replay; installation smoke checks cover the distributable.

Local release preparation passed: matching library/CLI tarballs, OpenAPI and revision/hash manifest. CI publishes the API image and CLI assets from one tag. Nothing has been published or deployed remotely.

What adding an operation requires

Add its schema and metadata to operations; implement the server dispatcher branch; add behavior and authorization tests. The generic CLI command, completion entry, OpenAPI description and MCP tool derive from that entry. A convenience CLI alias is optional and still calls the API.

What replacing persistence requires

Implement the repository’s atomic enqueue/claim and lease-fenced mutation semantics. Preserve owner filtering, immutable checkpoints and plan identity. Run concurrency and recovery tests against the new adapter. Returning the same TypeScript shape without these guarantees is insufficient.

What future sessions need

Start with AGENTS.md and docs/agent-context.md, then read the relevant port/source and tests. The context records the subscription/no-fallback decisions, credential setup, package ownership and unverified live evidence. Keep this architecture reference synchronized. Do not duplicate provider logic in CLI or transport handlers.

Native Codex ASR feasibility

External environment

Dedicated-container login/refresh/restart and live understanding need separate acceptance. No Neon attachment, registry publication or production deployment is claimed here.

Run and deploy

  1. Provide DATABASE_URL, a random MEDIA_OWNER_TOKEN of at least 32 characters, and MEDIA_PUBLIC_URL.
  2. Configure only the source/provider credentials you intend to use. Subscription providers require dedicated native CLI login.
  3. Apply the versioned media_v1 migration. The old database is reference only.
  4. Build the container with media tools and pinned native CLIs; start the API/worker process.
  5. Persist /data, /auth/codex and /auth/claude; terminate HTTPS at the configured public origin.
  6. Configure the CLI, or connect the agent to /mcp and approve access.

Compose binds the API to loopback port 4000. The container runs as a non-root user with a health check and graceful shutdown window. Native credential refresh writes back to the dedicated auth volumes.

Operational follow-through. The owner will provision Neon and attach its URL. Back up both PostgreSQL and the upload volume. Expired auth entries are pruned hourly. Abandoned workspaces need operator maintenance; persisted job history and uploads are not automatically deleted by normal job cleanup.
